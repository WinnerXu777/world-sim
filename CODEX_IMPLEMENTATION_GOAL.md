# Codex implementation goal: a persistent medieval village with interactive NPCs and god mode

This is a ready-to-use goal for a subsequent implementation run. The review task has not started this implementation or changed gameplay code.

## Goal prompt

Develop the existing Eden repository into a coherent, playable 3D medieval village in Godot, backed by its authoritative Python simulation. Deliver a 20–30 minute single-player experience with responsive movement, reliable character animation, a stable explorable scene, 8–12 named residents with persistent LLM-assisted interactions, and god mode that changes the same world and produces NPC consequences.

First read `ENGINEERING_REVIEW.md` for the findings and rationale. Then read and follow `implementation_0905.md` as the detailed execution plan, including its Stage 1 A–H and subsequent Stage 2 I dependency order, implementation contracts, acceptance gates, and completion checklist. Verify the review's findings against the current working tree before changing code. The feature list below summarizes scope; the detailed plan determines execution order. Preserve current user instructions as the highest-priority project direction, and document evidence-based deviations if the repository has changed.

Work incrementally through the milestones below. Preserve existing user changes, resident identities, tensor schemas unless explicitly migrated, and useful domain systems. Record baseline behavior and keep development/test saves separate from existing user data. Do not reset the current world for validation. Favor a complete small village over adding more disconnected systems.

## Release order: game first, models afterward

Stage 1 is the immediate priority: complete A–H in `implementation_0905.md` with deterministic NPC decisions, scripted dialogue, real crafting/inventory/memory, and UI-driven god powers. Deliver and verify the playable village without any LLM or TTS credentials. Preserve existing integration seams but defer new provider adapters, model routing infrastructure, free-form dialogue, and speech synthesis.

Stage 2 begins only after the playable-game Gate H passes: follow I0–I5 for world, resident, and fast-interaction models, then optional TTS. Stage 1 completion and Stage 2 completion must be reported separately. A working scripted game satisfies Stage 1; it does not claim live LLM integration.

## Required implementation and approach

1. **Separate gameplay from visual testing.** Introduce explicit gameplay, animation-QA, and render-fixture launch profiles. Gameplay starts or loads a save through New Game / Continue and runs the full simulation. Remove implicit calls to `/testing/render_test_village` from ordinary startup. Test routes and the virtual controller are development-only. Move player-following ground/backdrops and forced action holds into QA scenes. Keep real terrain, props, and NPCs visible at fixed world coordinates.

2. **Establish a reproducible character pipeline.** Inventory existing assets and select one complete humanoid rig/outfit and compatible clip set. Define rest pose, bind transforms, axes, units, root behavior, and clip metadata. Validate body coverage and skin bindings. Retarget/import once, then use cached animation resources. Build an AnimationTree for idle/walk/run, talk, attack, hit, fall, downed, get-up, and death with explicit priorities and interruption rules. Use actual velocity for locomotion blending and speed matching. Replace existing runtime correction paths only after comparison captures pass. Do not add more arbitrary per-clip bone offsets to conceal incompatible rigs.

3. **Make movement, camera, and spatial rules coherent.** Introduce a collision-aware player motor on the physics step and a separate visual presentation node. Use a versioned shared geometry/movement contract between Python and Godot. Define simulation-unit-to-meter conversion, speed, acceleration, slope/obstacle behavior, and facing. Start with ground-plane movement plus shared height/obstacle data; add surface IDs/portals where needed. Use camera obstruction handling instead of hiding all nearby actors/chunks. Extend existing input sequencing with last-applied acknowledgments and replay of unacknowledged inputs. Reset prediction on new world/possession epochs.

4. **Build one real village.** Author a connected square, smithy, tavern, farm, homes, and forest path from existing licensed assets. Use complete building prefabs with collision and interaction anchors. Map usable props to stable backend entity IDs. Keep scenery fixed when moving or orbiting the camera. Update chunks/entities incrementally and profile asset construction. Support one doorway/interior transition if required for the chosen interaction loop; defer arbitrary multi-level physics until its authority model is implemented.

5. **Stabilize the backend.** Extract simulation scheduling, transport endpoints, persistence, and bootstrap from `map_test.py` while preserving APIs through adapters. Keep one owner of live mutations. Route commands through typed validation and a bounded queue, apply them at tick boundaries, and publish committed events/results. Replace work-plus-sleep timing with a monotonic fixed-step scheduler and bounded catch-up. Add clean task shutdown. Run model and persistence work outside the tick's blocking path using immutable snapshots and result queues. Do not pass a mutable Engine into worker jobs.

6. **Make state durable and protocol behavior testable.** Fix failed resident writes being marked clean. Add save error reporting, retries, schema versions, backup/import of existing resident files, and coherent world checkpoints including tensors, IDs, RNG state, residents, inventory, tasks, and tick. Use SQLite transactions plus versioned snapshot manifests, or document an equally crash-consistent simpler implementation. Rebuild MemoryRAG from authoritative saves. Version command/state envelopes, distinguish received from applied inputs, use idempotent event/command IDs, and implement reconnect resync. Default to loopback and keep development endpoints unavailable in normal gameplay.

7. **Later Stage 2 only: implement multi-tier LLM behavior.** After Gate H passes, follow I0–I5 in `implementation_0905.md`: a world model handles world reasoning/decrees; an agent/resident model handles individual NPC decisions, goals, and commitments; a fast interaction model handles short dialogue and contextual reactions within those decisions. Keep deterministic execution authoritative and independent of inference. Configure providers/models, prompts, allowed outputs, queues, budgets, and live/mock/fallback status separately per tier, even if tiers initially share a model. Use asynchronous jobs with deadlines, cancellation, stale-result rejection, and bounded escalation. NPC context must respect personality, perceived facts, memories, and relationships. Validate every proposed action before committing. Add a separate optional TTS adapter for approved dialogue, with stable NPC voices, subtitles, interruption, and text fallback; voice failure cannot block gameplay. Never execute model-generated Python or arbitrary tools.

8. **Stage 1: deliver a complete interaction loop using deterministic decisions and scripted dialogue.** A player can ask the smith for a sword; the smith responds according to materials, trust, and current work. An accepted promise creates a validated task, reserves/consumes actual materials, drives movement and work animation, and transfers an actual item on completion. Missing resources or a damaged forge produce an understandable failure/replan. The NPC remembers the interaction after save/reload. Integrate the existing crafting, task, inventory, schedule, personality, and memory systems rather than duplicating them.

9. **Implement consequential god mode.** Add explicit transitions between embodied human control and an overhead/free god camera. Release and reacquire control safely; autonomous behavior resumes on release. Provide resident inspection, pause/time controls, heal, allowed-resource spawning, and weather changes. Reuse the validated decree/command path and return visible accepted/rejected/applied results. Preview broad effects and checkpoint irreversible changes. Feed committed consequences into NPC perception, memory, relationships, and task review. Stage 1 uses UI controls and typed commands. Add natural-language decrees in Stage 2, compiling into the same allowed operations.

10. **Package and verify the experience.** Add clear launch instructions, onboarding, interaction affordances, minimal inventory/conversation/god UI, and useful audio/visual feedback. Add automated tests for state transitions and authority boundaries, plus recorded in-engine validation. Repair the invalid ignore glob and document which assets/plugins are required for a clean checkout. Keep generated saves/captures out of source changes unless intentionally included as evidence.

## Definition of done

Apply gameplay criteria to Stage 1. Live-model, generated-dialogue latency, stale-model-response, and optional TTS criteria apply only to Stage 2; they must not delay the playable-game release.

- A normal launch and reconnect preserve the selected world; New Game is explicit. Full NPC and decree processing remains active in gameplay.
- The village is fixed in world space. Walking and turning the camera never drag the terrain or building set. Nearby NPCs remain visible and targetable.
- Fresh gameplay recordings show idle, walking, sprinting, diagonal movement, turning, stopping, conversation, attack, hit, fall, and get-up. No missing body parts, visible rig explosion, unexpected clip resets, or persistent obvious foot sliding in the supported character set.
- Player input responds locally within two rendered frames on the documented reference machine. Delayed/reordered inputs and reconnects do not duplicate actions or affect the wrong possessed actor. Authoritative collision prevents crossing a test wall.
- Tick work p95 stays below the 50 ms budget at the selected 20 Hz target for the documented initial population. A deliberately delayed model response does not stall movement, combat, or state delivery. Report frame time, tick time, queue age, model latency, fallback rate, and reconciliation error.
- Stage 2: dialogue either finishes within the chosen five-second target or produces a clear fallback while the world continues. No configured provider is reported honestly as mock/fallback; it cannot satisfy the live-LLM acceptance check.
- Stage 2: world and resident model routes are independently exercised with live configured providers; fast dialogue cannot bypass their capability/decision boundaries. Track costs and fallback behavior per tier. If optional TTS is undertaken after text-model integration, its boundary is implemented; enabled voice playback passes interruption, subtitle, and stale-audio tests, with live-provider verification reported separately.
- At least one resident completes the request-to-task-to-inventory loop and recalls the relationship-relevant interaction after restart. Invalid or stale model proposals cannot award items, damage targets, or alter a replacement world.
- The player can enter god mode, apply each supported power, observe consequences, and return to human control. At least one affected NPC changes behavior and later refers to the event.
- Locked-file and interrupted-save tests preserve the last complete save and retain unsaved changes for retry. World reload restores inventory, resident identity/memory, and ongoing task consistency.
- A 20–30 minute end-to-end playthrough is documented with fresh captures from normal gameplay, test results, reference hardware, known limitations, and exact launch commands. The initial target is 60 FPS at 1080p; measure it and report any remaining gap honestly.

## Execution discipline

Start with tickets A1–A4 in `implementation_0905.md`: isolate test saves, establish a reproducible baseline, separate gameplay/QA startup, and prove a fixed gameplay scene. Then continue through B–H in order with models disabled. Verify and record the playable-game gate before starting Stage 2 I. Add focused regression tests around each repaired boundary. Keep milestones reviewable and maintain `IMPLEMENTATION_PROGRESS.md` with ticket status, changed paths, verification commands/results, evidence, and remaining acceptance criteria. Continue implementation rather than stopping after scaffolding or planning; do not claim the overall goal complete until the detailed plan's gates and this goal's definition of done are satisfied.

Do not claim gameplay completion based on isolated QA screenshots, fabricated task outcomes, disabled simulation, or camera-following scenery. Deterministic/scripted dialogue backed by real systems is the intended Stage 1 implementation. Do not claim Stage 2 completion from mock dialogue alone. Do not train a custom model, migrate engines, introduce multiplayer, or expand the world before the village loop works. If a real provider or asset is unavailable, finish independent work and identify the exact remaining requirement; do not silently substitute a mock and mark the overall goal complete.

# G-005: resources in authored maps (design [GAP]; no loader, validator, map or asset edited)

Author: harness worker (837dca). Question from the orchestrator: how do wells, farm plots, berry bushes, trees, ore, fish, stores and safe places become real, queryable resources, from the authored map file to `m_tensor`, the legacy resolvers, the harness `World`, and the Effects that deplete and regrow them. Everything below was read from the code at HEAD; nothing here is implemented. File paths are relative to `at_the_beginning/`.

## 0. What the code does today (facts the design rests on)

* **Authored objects are inert.** `systems/map/authored.py::instantiate_authored_entities` turns every *interactive* map entity into an `M_MAP_OBJECT` (26) row, or `M_STORAGE_CASE` (25) for kinds `storage/chest/storage_case/crate`, with `register_geo=False` (no `MAP_GEO` circle) and no resource columns. Non-interactive entities (the 8 trees, buildings, decorations) are never instantiated. This is why the task resolvers return `None` for food, water and safe targets in the village (Model plane finding F-2).
* **The resolvers read the tensor, not the map.** `Engine._resolve_task_resource_target` (`map_test.py` ~2040) filters `map_geo` neighbours by `M_TYPE` (food: grass/forest/beach/lake/farm/house/village; water: lake/well/farm/village), then needs `M_RESOURCE_FOOD` (col 10) or `M_RESOURCE_WATER` (col 11) `> 0`, not burning (col 8), not flooded (col 9); score = distance - 0.1*resource - 0.03*fertility. `_resolve_task_safe_target` uses `DEFAULT_SAFE_TYPES = {grass, forest, beach, house, village, farm, well}` (`systems/perception/queries.py`). Everything goes through `map_geo.entities_in_radius`, so **an entity with no `MAP_GEO` circle is invisible to all of it**.
* **Eating and drinking** (`instinct_eat` -> `eat_from_current_entity(map_geo.entity_at)`) is type-agnostic: any entity whose geo circle covers the resident's tile and has `food > 0` feeds him (+20 hunger relief, -1 food). `instinct_drink` -> `_nearest_geo_entity` limited to `DRINKABLE_TYPES = {M_LAKE, M_WELL}`. `tool_harvest_food` uses `FOOD_SOURCE_TYPES = {grass, forest, beach, lake, farm}` (defined twice: `instincts_and_tools.py`, `systems/survival/navigation.py`).
* **Regrowth** (`systems/nature/ecology.py`): `apply_resource_regrow` (natural types + farm + well, `fertility/100 * 0.015 * food_multiplier`, cap 100, not burning); `apply_water_cycle` (lakes `growth_rate * max(fertility,25)/100`, wells `growth_rate` once `S_BUILD_PROGRESS >= 100`, farms grow food `0.10 * max(water/100, .25)` while `water > 0.04`, consuming 0.04 water per tick). Registered as `instinct_resource_regrow` (82) and `instinct_water_cycle` (83).
* **Roster residents ignore all this**: they eat and drink through `systems/roster/needs.py` trips to anchors (`village:use_well`), with a free ration as fallback. Decision-driven (`agent`) residents (D-008) go through the affordance layer, which reads kind-based authored entities (`GATHER_NODES`, `STORAGE_KINDS`, `BED_KINDS` in `systems/affordance/config.py`) and `Services.typed_resources("food"|"water", ...)` over tensor entities. So tensor resources are what both the legacy resolvers and the affordance layer need.
* **Format.** `world_map/parse.py::_parse_entities` keeps only `id, kind, interactive, position, sprite, interact_radius`; any other key inside an entity is dropped silently (no warning); unknown *top-level* keys give a warning "unknown top-level key (ignored)". `map_contract.register_world_map` copies entities into the registry as `{id, kind, interactive, position, interact_radius}`. File hash and revision are recorded in saves (`persistence/map_guard.py`): a changed `revision` or a changed sha256 at the same revision makes Continue refuse in the production profile (development profile or `EDEN_ALLOW_MAP_MISMATCH=1` loads with a notice).
* **The four maps already contain resource-bearing kinds**, all interactive: `starter_village` (revision 3, 48x36 tiles): `well` x1, `berry_bush` x1, `wood_pile` x1, `stone_pile` x1, `campfire` x1, `storage` x4, trees x8 (non-interactive); `smith_interior` (rev 2): `iron_pile`, `storage`, `bed`, `forge`, `anvil`; `village_lodge_interior` (rev 1): `bed` x3, `storage`; `west_cottage_interior` (rev 1): `bed` x2, `storage`.

## 1. Entity kinds with resource semantics, and how the 0.2-draft format expresses them

### 1.1 The kinds
One optional object on an entity: `"resource"`. Its `type` selects the semantics; the other keys are overrides of per-type defaults (so most entries are one line). Existing kinds get **defaults by `kind`**, so the 4 maps do not have to change to gain semantics (see 1.3).

| `resource.type` | default for `kind` | tensor type | stock columns written (defaults) | gather / use |
|---|---|---|---|---|
| `well` | `well` | `M_WELL` (23) | water 80 (`INITIAL_WATER_WELL`), growth_rate 0.08, `S_BUILD_PROGRESS` 100 (the water cycle ignores wells below 100), durability 100 | drink (legacy `DRINKABLE_TYPES` already includes 23) |
| `farm` | `farm_plot` (new) | `M_FARM` (22) | food 0..`amount`, water 30 (`INITIAL_WATER_FARM`), growth_rate 0.10, build 100 | eat from the plot; irrigation consumes its water (legacy), so a plot needs a water refill or it stops: see 3.3 |
| `bush` | `berry_bush` | new `M_RESOURCE_NODE` (27), `node_kind` 1 | food `amount` (default 40), growth_rate 0.02, item `berries` | eat in place (legacy eat is type-agnostic) or gather -> `berries` |
| `tree` | `tree` (when `interactive: true`) | node, `node_kind` 2 | stock `amount` (default 60), growth 0.005, item `wood_bundle` | gather -> `wood_bundle` |
| `wood`, `stone` | `wood_pile`, `stone_pile` | node, kinds 3, 4 | stock 30, growth 0 (finite unless authored otherwise), items `wood_bundle`, `stone_chunk` | gather |
| `ore` | `iron_pile` | node, kind 5 | stock 20, growth 0, item **`iron_ore`** (as built, section 10; `GATHER_NODES` still names `iron_ingot` for the legacy kind-based path). The recipes and the smith loop consume `iron_ingot` and **no smelting step exists yet**: a `smelt` verb (`iron_ore` -> `iron_ingot`) is a prerequisite before gathering ore feeds the smith loop | gather |
| `fish` | `fish_spot` (new) | node, kind 6 | food/stock 30, growth 0.03, item `fish_catch` (edible per `EDIBLE_ITEMS`) | gather (needs adjacency to water: validator warning) |
| `stock` | `storage`, `chest`, `crate`, `storage_case` | `M_STORAGE_CASE` (25), unchanged | none in the tensor; `"stock": {"rations": 6}` seeds the inventory record | seeded once at genesis (see 3.4) |
| `safe` | `bed`, `shelter` (kind-based today) / `hearth` | `bed`: stays `M_MAP_OBJECT` (kind-based, as `BED_KINDS` now); `shelter`: `M_HOUSE` (20), build 100, `S_SHELTER_CAP` = `capacity` | legacy `best_safe_entity` already prefers houses (+25 bonus) | rest/sleep verbs (affordance) |

New tensor columns for the node type (all free in the 32-column entity tensor; 13-31 are reserved/unused for structures): `M_NODE_KIND` 13, `M_NODE_STOCK` 14 (non-edible stock such as wood), `M_NODE_CAP` 15, `M_DEPLETED_TICK` 16 (tick when stock reached 0, -1 otherwise; used for the edge-triggered events in 3.3). Edible nodes keep their stock in `M_RESOURCE_FOOD` (col 10) so every existing food query works unchanged; non-edible nodes use col 14.

### 1.2 JSON (additive, optional, validated) - CORRECTED in step 1
Step 1 found that the chunk generator already writes `resource` (a STRING), `amount`, `tiles`, `radius` on its entities, with kinds `forest`, `ore_vein`, `stone_outcrop`, `berry_patch`, `fish_spot`, `reed_bed`, `mushroom_patch` (real chunks have `ore_vein` amounts above 100 and radii above 60). A nested `resource` object would have collided with that and with the chunk golden bytes, so the authored form uses the **same flat keys**:
```json
{"id": "family:bush_east_1", "kind": "berry_bush", "interactive": true, "position": [312, 168], "sprite": "a2/sprites/berry-bush-a2-v1.png",
 "interact_radius": 12, "resource": "berries", "amount": 24, "cap": 40, "regrow": 0.02, "radius": 6}
```
Keys (implemented in `world_map/resources.py`, all optional, interactive entities only): `resource` = `water` (kind `well`), `crops` (`farm_plot`, `farm`), `berries` (`berry_bush`, `berry_patch`, `bush`), `wood` (`tree`, `forest`, `wood_pile`), `stone` (`stone_pile`, `stone_outcrop`), `ore` (`iron_pile`, `ore_vein`, `ore_node`), `fish` (`fish_spot`), `reeds` (`reed_bed`), `mushrooms` (`mushroom_patch`); `amount` (0..1e6 units), `cap`, `regrow` (0..10/tick), `radius` (0..256), `tiles`, `item`, `water` (crops only, 0..100); `stock` (`{item: qty}`, storage kinds); `capacity` (1..32, `bed`/`shelter`/`hearth`). The "type" column of the table in 1.1 is the `resource` name here (well -> `water`, farm -> `crops`, bush -> `berries`, tree/wood/stone/ore/fish as listed; `stock` and `safe` are the `stock`/`capacity` keys). Units above a tensor column's cap (an ore vein of 276) are the loader's problem (step 2: clamp the column, keep the rest in `node_stock` or refuse). Rules: wrong resource for the kind, unknown names, ranges, and the keys on a non-interactive entity are errors with paths like `entities[3].amount`. The normalised declaration is `Entity.resource = {"name": ..., ...}` and `map_contract` registers it on the entity dict only where declared.

### 1.3 Backward compatibility with the 4 existing maps and Continue
* **No file edit needed** for the kinds above: with `EDEN_MAP_RESOURCES=1` (default off, D-002 style) the loader applies the *defaults by kind* to the entities already authored. The 4 files keep their bytes, sha256 and revision, so `map_guard` is untouched and old saves still load.
* An old save already contains those entities as `M_MAP_OBJECT` rows (ids are restored from `_entity_uid_by_slot`, and `instantiate_authored_entities` skips ids that are present). The loader therefore needs an idempotent **upgrade step** for present ids: if the row is still `M_MAP_OBJECT`, rewrite type, columns and geo once. It must be a no-op for rows already upgraded. A save written with the flag on and loaded with the flag off keeps type 27/23/22 rows; legacy code treats unknown types as inert, like `M_MAP_OBJECT` (tested in the design's test plan).
* **Adding explicit `resource` objects to a map file** (what the Codex author will do for new content) changes the bytes: the map `revision` must be bumped, and an old save of that map is refused by Continue in the production profile (that is the intended guard). New maps (the S-1 family map, generated chunks) carry no such history.
* The strict golden (seed 1008, `starter_village`) changes when the flag is on (the well, bush, wood/stone piles become real; residents are roster-driven, so the effect is small but nonzero: the nature loops regrow them). Flag off it must stay byte-identical; with the flag on a new golden is recorded under a decision, never regenerated silently.
* Client: `GET /map_file/{id}` serves the exact bytes, so a Godot/JS loader that reads entity dicts sees an extra `resource` key; it must ignore unknown entity keys (relay note for the client owner, like H-003). The `state.entities` stream gets `type: 27` rows: the client needs a sprite/label mapping for `node_kind` (relay).

### 1.4 Chunk documents: extra top-level keys (H-002, backend side)
Chunk documents (`./worldgen.md`) are 0.2-draft plus `chunk`, `data`, `pinned_map`. Today `parse.py` warns "unknown top-level key (ignored)" for each. Change (additive, no version bump, `0.2-draft` stays):
* `_TOP_KEYS` gains `chunk`, `data`, `pinned_map`; they stop warning.
* They are **parsed into `WorldMap.extras`** (a new frozen, `compare=False` field, `{"chunk": {...}, "data": {...}, "pinned_map": str|None}`) so a chunk-aware loader reads them from the validated object instead of re-parsing the JSON.
* Light structural validation (errors): `chunk` is an object with integer `cx`, `cy`; `data` is an object; `pinned_map` is a string matching `ID_PATTERN`; a document with `pinned_map` must have empty layers, no walls, no entities (it is a pointer). Everything else inside those blocks is opaque to the validator (the worldgen owner defines it; `check_map_bytes` on the real chunks stays at 0 errors, which `tests/test_worldgen_*` already assert).
* Chunk entities may carry `resource` objects like any map, so generated forests/ore/fish spots become real resources through the same loader; chunk ids are `chunk:cx:cy:...` and never collide with `e_NNNNNN`.
* Files: `world_map/parse.py`, `world_map/schema.py` (`extras`), `world_map/README.md`, `tests/test_world_map_v02.py`-style tests (new file `tests/test_world_map_chunk_keys.py`).

## 2. Loader -> `m_tensor` -> resolvers -> harness

### 2.1 Loader
New module `systems/map/resources.py` (pure data + one function): `RESOURCE_KINDS` (table of 1.1), `defaults_for(kind)`, `columns_for(resource)` -> `(m_type, scale, col_vals)`. `instantiate_authored_entities` calls `columns_for` when the flag is on; for resource kinds it calls `entity_born(..., register_geo=True, col_vals=...)` with a **circle** `MAP_GEO` registration of the declared `radius` (instead of `register_geo=False`), so `entities_in_radius`, `entity_at`, shelter and perception queries see it. After creation it sets `engine._entity_uid_by_slot[slot] = entity["id"]` as today, so ids stay stable and saves restore them.
Geo cost: each registered circle adds tile-mask entries; a village has fewer than 20, a streamed chunk fewer than 16 entities (worldgen cap), so no per-tick cost (geo is queried by the same loops as now).

### 2.2 What the legacy resolvers need (exact edits in section 4)
* Resource type filters: add `M_RESOURCE_NODE` to `_task_resource_type_ids("food")` (`map_test.py`), to both `FOOD_SOURCE_TYPES`, and to the regrow type loop in `ecology.py` (or replace that loop by the harness system of 3.3). Water: wells are already in `DRINKABLE_TYPES` and in the water filter.
* Safe places: `shelter` -> `M_HOUSE` is already in `DEFAULT_SAFE_TYPES`; beds stay kind-based (affordance), no resolver edit.
* `best_resource_entity`/`best_safe_entity` score from the same columns; no edit.

### 2.3 What the harness `World`, selectors and Services see
`harness/adapter.py::ENTITY_COLUMNS` gains `node_kind`, `node_stock`, `node_cap`, `depleted_tick`; `EngineWorld.config["resource_model"]` gains `node_types` and the per-`node_kind` item table, so `bounty_area`/`scarcity_area` (which already work on "carrier" entities by `natural_types/other_types`) treat nodes like any carrier. Typed selectors already select entities by `type` and by `food`/`water` comparisons; a node is `type == 27` plus `node_kind`. `Services.typed_resources("food"|"water")` (Model plane) reads these columns, so it finds the new rows with no change on their side. Reads are by stable id (`entity_id` = the map id, e.g. `family:bush_east_1`), which is also what `Transfer`/`Task` effects name.

## 3. Regrowth and depletion as Effects, with item permits

### 3.1 Regrowth (system)
`harness/resources.py` registers `resource_regrow` (`@system`, phase `world`, `writes=("entities.food","entities.water","entities.node_stock")`, `every=1`): selects live nodes/wells/farms/natural carriers below cap and not burning, builds **one `Delta` per field** with per-id amounts (`fertility/100 * RESOURCE_REGROW_RATE * multiplier` for natural types, `growth_rate` for wells and nodes, the farm water rule) and `FieldSpec(hi=cap)` on `food`, `water`, `node_stock` (entity table, today none). Same exactness approach as S3 (`./s3_s5_taskbridge_design.md`): per-id float32 amounts computed in the legacy operation order, one applier run per field, bit-for-bit test against `apply_resource_regrow`/`apply_water_cycle` on random states, then the registry-wrapper swap behind `EDEN_HARNESS_RESOURCES=1` (it replaces `instinct_resource_regrow` (82) and `instinct_water_cycle` (83) by one entry at 82). The `food_multiplier`/`water_multiplier`/`farm_multiplier` modifiers (`engine._nature_state`) are read exactly as now. This is a separate step after S3 is measured; the nature loops stay legacy until then (the node type is added to their type loop in the meantime).

### 3.2 Depletion
Depletion is an Action effect, never a tensor write by hand: `eat_from_node` = `[Delta(entities, [node], food, -EAT_RESOURCE_COST), Delta(humans, [actor], hunger, -EAT_HUNGER_RESTORE)]` (legacy numbers), and `gather` = `[Delta(entities, [node], food|node_stock, -k), Transfer(item=<node item>, src=None, dst=<actor>, qty=k)]` with the **item permit** below. Both are validated atomically (`atomic=True`: if the node is empty or the pack is full nothing applies; the failure reason is `no_room`/`not_live`/`empty` as existing effects already report).

### 3.3 Events and scarcity
When a node crosses 0 (`depleted_tick` set) or recovers above 25% of `cap`, the system emits `Emit("resource_depleted"|"resource_regrown", actors=(node_id,), place=(x, y), visibility="local")` with `event_id=f"res:{node_id}:{tick}"`. These feed gossip and reputation (S-1 consequences) through the existing `EventLedger`; the witnesses rule is the god-event one. Farm plots: because legacy irrigation drains `water` and nothing refills it, a plot whose `water` reaches 0 stops producing; the design offers either `resource.irrigated_by: "<well id>"` (the regrow system tops up the plot's water from a well with a Delta pair, conserving a "water unit" count) or no refill (scarcity by design for S-1). Decision for the orchestrator: default no refill.

### 3.4 Item permits (conservation)
* `gather` declares `produces=("berries","wood_bundle","stone_chunk","iron_ingot","fish_catch")` and runs with `ItemPermit(produce={item: k})`, k capped by the stock removed in the same effect list (a test asserts items created == stock units removed x yield, yield 1 by default). Nothing else may create these items.
* `eat_from_node` creates and destroys no item (a stock unit becomes hunger relief), so its permit is empty and any Transfer in it is refused.
* Genesis seeding of `stock` objects: one `Transfer(src=None, dst=<container>, ...)` batch under `ItemPermit(produce=...)` with `cause="genesis:map_stock"`, applied once per world (idempotent via a marker in the container record); conservation is checked against the declared totals (`world.items.total`).
* Regrowth creates no item (it restores a column), so it needs no permit; the conservation check stays vacuous and cheap.

## 7. Authoring note for the map author (flat resource keys)
Everything here is checked by the validator today (`.venv/Scripts/python.exe tools/validate_map.py MAP.json --base-dir myassets`). The engine does not read the keys yet (G-005 step 2); write them now, they are validated and kept.

**Rules.** Put the keys directly on the entity (never a nested object). Only `"interactive": true` entities may carry them. Every entity still needs `id` (unique, not `e_NNNNNN`), `kind`, `interactive`, `position` (inside the map). Editing a shipped map changes its bytes: bump its top-level `revision` by 1. A new map or a generated chunk has no history, start at 1.

| entity `kind` | `resource` value | other keys that make sense | what it will be |
|---|---|---|---|
| `well` | `water` | `amount` (water, default 80), `regrow` (default 0.08) | drinkable source that refills |
| `farm_plot` (or `farm`) | `crops` | `amount` (food, default 0), `water` (default 30), `regrow` (default 0.10) | grows food while it has water; water is not refilled (decision G-005) |
| `berry_bush`, `berry_patch`, `bush` | `berries` | `amount` (default 40), `cap`, `regrow` (default 0.02), `radius` | edible and gatherable (item `berries`) |
| `mushroom_patch` | `mushrooms` | same as berries | edible, gatherable |
| `fish_spot` | `fish` | `amount`, `regrow` (default 0.03), `radius`; put it beside water | gatherable (item `fish_catch`) |
| `tree`, `forest`, `wood_pile` | `wood` | `amount` (default 60 for a tree, 30 for a pile), `regrow` (trees 0.005, piles 0) | gatherable (item `wood_bundle`); trees must be `interactive: true` to count (village trees stay decoration) |
| `stone_pile`, `stone_outcrop` | `stone` | `amount` (default 30) | gatherable (item `stone_chunk`) |
| `iron_pile`, `ore_vein`, `ore_node` | `ore` | `amount` (default 20) | gatherable (item `iron_ingot`) |
| `reed_bed` | `reeds` | `amount` | gatherable |
| `storage`, `chest`, `storage_case`, `crate` | none | `stock`: `{"rations": 6, "crop_bundle": 2}` (item names lower case, quantity 1..10000) | container; the stock is placed in it once when the world is created |
| `bed`, `shelter`, `hearth` | none | `capacity` (1..32 occupants) | rest/safe place |

Allowed everywhere a `resource` is given: `amount` (0..1,000,000), `cap` (> 0, not below `amount`), `regrow` (0..10 per tick; 0 means finite), `radius` (0..256 units, the circle in which a resident counts as "at" it; default 6 to 12 by kind), `tiles` (integer, informational), `item` (lower-case item name, normally leave it out so the kind decides). A key without `resource` is an error; `water` only on crops; `stock` only on storage kinds; `capacity` only on shelter kinds.

**Examples.**

```json
{"id": "family:bed_1", "kind": "bed", "interactive": true, "position": [24, 40], "capacity": 1}
```

## 10. Dedicated item kinds (berries, mushrooms, reeds, ore): effort and save compatibility
Today `systems/map/resources.ITEM` maps berries and mushrooms to `crop_bundle`, reeds to `fiber_bundle`, ore to `iron_ingot` because `systems/inventory/schema.py::ITEM_KIND_DEFS` has no such kinds. What dedicated kinds would take (read from the code, not built):
* **Schema:** four entries in `ITEM_KIND_DEFS` (`berries`, `mushrooms` as perishable food with tags like `fish_catch`, `reed_bundle` as material/fiber, `iron_ore` as material/metal; label, stackable, max_stack, tags, unit_weight, value), about 40 lines in one legacy file.
* **Save compatibility:** inventory records store each stack's `kind` string; `INVENTORY_SCHEMA_VERSION` stays 1. Existing saves keep loading unchanged (adding a kind is additive). A save made after the change that holds a new kind cannot be loaded by code without it (`build_item_stack` raises `KeyError: unknown inventory item kind`), so this is forward-only; no migration code is needed.
* **Edible kinds** (berries, mushrooms) must also join `systems/affordance/config.py::EDIBLE_ITEMS` and `systems/tasks/families/survival.py::EDIBLE_ITEM_KINDS`; a drift test (`tests/test_affordance_unit.py`) forces them to stay equal. `systems/decision/features.py` computes `has_food` from `EDIBLE_ITEMS`, so a feature value changes for residents holding the new kinds (no schema change; Tier 1 logs recorded with such items would differ). The legacy `eat_food` handler's per-item hunger relief was not read; it must be checked before an edible kind is added.
* **Why it matters now (a hazard of the current mapping):** `crop_bundle` is also the farmer's output in `systems/tasks/families/occupation.py` (cargo checks at lines 382 to 410, 616, 876). A resident who gathers berries as `crop_bundle` holds what the farming tasks read as farm cargo, so a farmer task chain could try to deliver gathered berries. With a dedicated `berries` kind that coupling disappears. Until then S-1 content should not mix farmers and berry gathering in one resident.
* **Rest of the repo:** `systems/roster/load.py` and `tests/test_commission_data.py` read `ITEM_KIND_DEFS` for validation, so new kinds need no edit there; client item names or icons were not searched.
Estimate: one legacy file (schema), two constants kept equal, two small drift tests, one design note; about half a day of work plus a Tier 1 feature check; no save migration. Decide when S-1 needs berries or mushrooms as items distinct from crops.
Done (G005 HARNESS-NEXT b): `berries`, `mushrooms`, `reed_bundle`, `iron_ore` are in `ITEM_KIND_DEFS`; `berries` and `mushrooms` are appended to both edible lists (`("rations", "fish_catch", "crop_bundle", "berries", "mushrooms")`, so the old eating order is unchanged); `systems/map/resources.ITEM` maps berries/mushrooms/reeds/ore to the new kinds and nothing yields `crop_bundle` (tests: `tests/test_harness_item_kinds.py`). Consequence to know: ore yields `iron_ore`, not `iron_ingot`, and no smelting step exists, so gathering `smith:iron_pile` (ore kind) no longer gives the smith loop its ingot; the smith loop does not use nodes today (flag off). The eating relief of the new foods is the same `EAT_HUNGER_RESTORE` as any pack food (the `eat` verb uses one constant for every edible kind). Fish nodes still yield `fish_catch`, which is also the fishers' cargo.

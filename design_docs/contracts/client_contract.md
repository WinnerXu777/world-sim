# 1008 client contract: chunks, window, spaces (for the Godot client agent)

Written 2026-10-08 by the Harness worker [837dca], on the orchestrator's request (SPACES-DEC item 4). Source of truth for the backend side: `../designs/spaces_window_design.md` (sections 1, 3, 4) and `../designs/worldgen.md` (chunk format). This file is self-contained for a client implementer.

**Status column used below.** `IMPLEMENTED` = in the repo, tested (commit given). `PROPOSED` = agreed in the design, not built; the wire shape may still change before its phase lands, and the phase is named. Do not code against a PROPOSED item without checking this file again.

All new behaviour is behind flags, default off; the legacy finite world (`/bootstrap`, `/get_map`, `/map_file/{id}`, `/frame`, `/map_delta`) is unchanged when they are off.

## 1. Geometry and ids (IMPLEMENTED in the generator, `../designs/worldgen.md` section 1.1)
- One **chunk** = 32 x 32 tiles = 256 backend units = 1536 px at 48 px tiles. 8 units per tile.
- Address: integer pair `(cx, cy)`, any sign, Python int range (use int64; the server accepts `abs <= 2**40`). `chunk_id` is the string `"cx:cy"` (e.g. `"-1:3"`). Map id inside the document: `chunk_-1_3`.
- World tile of chunk tile `(i, j)` (column i, row j): `(cx*32 + i, cy*32 + j)`. Axes: origin top-left, +x right, +y down; layers are row-major `tiles[row][col]`.
- Positions inside a chunk document are chunk-local units in `[0, 256)`, multiples of 1/16.

## 2. Routes (IMPLEMENTED, commit d93ae46, flag `EDEN_CHUNK_ROUTES=1` on the backend; without it both routes answer 404)
### `GET /chunks?cx0=&cy0=&cx1=&cy1=` (inclusive chunk rectangle)
Response `200`:
```
{"ok": true, "world_seed": "1008", "generator_version": "0.1.0", "chunk_tiles": 32, "units_per_tile": 8,
 "chunks": [{"chunk_id": "0:0", "revision": 0, "url": "/chunk/0/0", "sha256": "<hex>"|null, "state": "ready"|"pending"|"pinned_map", "pinned_map": "<map id>" (only when state is pinned_map)}, ...]}
```
- Order: rows top to bottom, columns left to right (`cy0..cy1`, then `cx0..cx1`).
- `state: "pending"` (and `sha256: null`) = the server has queued generation, nearest the window centre first; ask again after a short delay (50 to 200 ms). The query itself raises the priority of the chunks it lists. `ready` = bytes can be fetched now. `pinned_map` = an authored area; fetch the map from `/map_file/<pinned_map>` (the chunk document itself is then only a pointer plus empty layers for partly pinned chunks; see `../designs/worldgen.md` section 5).
- `revision` is 0 until the server can change a chunk after generation (player edits, depleted resources; not built). A changed chunk will have a new `sha256` and a higher `revision`.
- Limits: at most 15 x 15 chunks per query. Errors (JSON `{"ok": false, "reason": ...}`): `400 window_too_large`, `400 invalid_window` (max < min), `400 coordinate_out_of_range`, `422` for non-integers.
- `world_seed` is a decimal **string** (JSON numbers above 2^53 lose precision in GDScript). Do not parse it as a float.

### `GET /chunk/{cx}/{cy}`
- `200` with the exact chunk bytes (`application/json`, canonical JSON, ASCII), headers `ETag: "<sha256>"` and `Cache-Control: no-cache`. The ETag is the quoted SHA-256 of the response body (same scheme as `/map_file/{id}`).
- Send `If-None-Match: "<sha256>"` (a weak `W/"..."` tag and `*` also match) to get `304` with an empty body. Recommended cache key on the client: the sha256. A chunk you already hold with the sha256 from `/chunks` needs no request at all.
- `503 {"ok": false, "reason": "chunk_pending"}` + `Retry-After: 1`: generation did not finish within 2 s (cold start of the worker processes); retry after the delay. `500 chunk_failed`: generation raised; retry once, then treat the chunk as unavailable (draw fog). `400 coordinate_out_of_range`.
- Hash and bytes are deterministic: same seed, same `generator_version`, same coordinates give the same bytes on every machine. If `generator_version` changes between sessions, drop the cache.

### Chunk document (summary; full spec in `../designs/worldgen.md` section 1.3)
`format_version "0.2-draft"`, `layers` (`terrain`, `decoration` (empty in 0.1), `footprint`) as int16 grids of palette ids (palette id -> `myassets`-relative png), `walls` (collision boxes in chunk-local units), `entities` (aggregated resource features and points of interest), `chunk` header, `data` (`biome`, `edges` autotile masks, `props`, `spawns`, `pois`, `caps`). It passes the existing `world_map` validator, so the existing map loader path can read it; unknown top-level keys (`chunk`, `data`) must be ignored by older readers.
- **Rule (PROPOSED, needs your agreement): draw tiles, props and the visual layers from the chunk document; take ENTITY STATE (positions, stock, depletion) only from the map delta (section 4).** The chunk's `entities` list is the generator's description of what the server will turn into entity rows; the rows are authoritative and change at runtime. Drawing both would draw every feature twice.

## 3. Windows: what the client sends and caches (IMPLEMENTED routes, PROPOSED policy)
- Render ring (client only): the camera rectangle plus one chunk. Ask `/chunks` for that rectangle whenever the camera enters a new chunk; fetch bodies only for hashes you do not hold.
- The server keeps its own simulation ring (about 5 x 5 chunks around the controlled actor) and prefetches ahead of travel; the client does not control it. A chunk you can see but the server has not integrated into the simulation may have no entities yet: draw its tiles, expect entities to arrive in the map delta.
- Build tile layers incrementally (a few chunks per frame). Unload client chunks beyond render ring + 1 (hysteresis).

## 4. Frames and the moving origin (IMPLEMENTED in P5, `harness/window_wire.py`, flag `EDEN_WINDOW=1`; proven end to end against a real server by `tools/live_smoke_window.py`: stamps, chunk routes, 409, save and restore, a player walking 3 400 units with four re-bases)
Still PROPOSED inside this section, not built: the coarse simulation of dormant residents (P6; the interim freeze is built, see the dormant residents bullet). Built since (R6.6, `harness/window_wire.py`): the integrated chunk set on the wire, `window.integrated` (void barrier bullet). Built since this text was written: `maps[]` and `spaces[]` rows carry `window_shift` under `EDEN_WINDOW`; the primary map keeps its registration `origin` and records the shift (the client rule for using it is the open sync item, see `../designs/spaces_p4_p5_gap.md` section 11 (d) and (f)).
The tensors on the server hold positions **relative to a window origin** (an integer chunk pair) so numbers stay small; the origin moves ("re-base") about every 25 s of walking. **The window follows the controlled human** (the incarnated or possessed player) when there is one, and the mean of the residents only when there is none: the origin moves to the player's chunk once it is more than 2 chunks from the current origin, so a player can walk away from the village indefinitely (measured: 3 400 units east, epochs 0 to 4). Residents left behind keep their absolute positions and ids; once they lie outside the fixed frame (about 5 chunks from the origin) they are no longer simulated terrain-wise and their chunks are unloaded, and they are still listed in `/frame` `agents[]` with their (now far, possibly negative) window-local coordinates: draw only what is near the camera, do not clamp or drop them. They are integrated again when the player walks back. Wire contract:
- Every `/frame`, `/map_delta` and `/bootstrap` payload carries `window_origin: [ox, oy]` (integers) and `window_epoch: n` (integer, +1 on every re-base). All positions in that payload are floats local to that origin.
- Absolute position = `origin * 256 + local`, computed by the client in int64 plus float (never one float32 of the sum).
- A re-base shifts every position by a whole multiple of 256 in a single payload and increments the epoch in that same payload, so a payload never mixes epochs. Keep entities by id; on an epoch change, re-express your cached local positions with the new origin (shift = `(old_origin - new_origin) * 256`), or simply re-read them from the payload.
- Requests that carry world coordinates (`POST /view/window`, `/human_view/window`, `/control/input` targets) must send `window_epoch`; the server answers `409 {"ok": false, "reason": "stale_window_epoch", "window_origin": [...], "window_epoch": n}` when it moved since (the client re-sends in the new frame). Behaviour for requests without the key: treated as the current epoch.
- `/bootstrap` gains `world: {"infinite": true, "chunk_tiles": 32, "units_per_tile": 8, "generator_version": "...", "world_seed": "<string>", "window_origin": [ox, oy], "window_epoch": n}`. Without `world.infinite` the world is the legacy finite 1200 x 900 frame and nothing in this section applies.
- **Entities are keyed by their stable id strings** (`e_NNNNNN` for legacy rows, `c<cx>_<cy>:<kind><n>` for chunk features). **Never key anything on the numeric slot.** An entity leaving the simulation window (unload) arrives as an ordinary removal in the map delta; the same id may reappear later (same feature, same id) when the chunk is integrated again.
- **Void barrier.** The server will not let an actor walk into a chunk it has not integrated: invisible wall boxes sit along the edge of the integrated area. Draw fog (or the chunk's tiles without entities) beyond it; the barrier is lifted when the chunk arrives. **The integrated set is on the wire (IMPLEMENTED, R6.6, `EDEN_WINDOW` only)**, as a nested key, never a dotted one: `"window": {"integrated": ["cx:cy", ...]}`, absolute chunk coordinates as `"<cx>:<cy>"` strings (the `/chunks` chunk id), sorted numerically by `(cx, cy)`, no positions. An incremental `/map_delta` carries it only when the set changed since the previous delta (a set-only change still advances `state_version`, with empty `upserts` and `removed`); a full, reconnect or stale-version `/map_delta` always carries the current set; `/bootstrap` carries it as `world.window.integrated`; `/frame` never does. A re-base alone does not change it (the ids are absolute). Timing: a chunk that brings entity rows reaches the delta in the same tick as its rows; a chunk that brings none (open water) can reach it up to `MAP_DELTA_EVERY` (20) ticks, about 1 s, after the barrier lifted, so treat the set as a fog hint, not as the collision truth. Without `EDEN_WINDOW` the key is absent.
- **Dormant residents.** Residents outside every simulation ring are not in the frames (they are simulated coarsely on the server). They appear, with their usual id, when a ring reaches them; do not interpret absence as death. (P6.)

## 5. Spaces (IMPLEMENTED in P3, backend flag `EDEN_SPACES=1` with `EDEN_PERCEPTION_BOUNDED=1`; default off)
- Overworld = space `0`. Each interior is its own space (the primary map is 0, the secondaries 1, 2, ... in the order the backend registered them). **Coordinates:** positions stay in the one layout frame the client already handles; each interior sits at its own origin (`maps[].origin`, as today). Space-local coordinates are `position - spaces[].origin`. A later phase (P5) will allocate interior origins from a pool outside the window range, so never hard-code origins; read them from `spaces`.
- Every human in `/frame` `agents[]`, every animal in `animals[]` and every entity in the map payloads (`/bootstrap` `map.entities`, `/map_delta` upserts) carries `space` (int). With the flag off the key is absent (treat as 0). Draw only the space of the controlled actor; rows of other spaces overlap numerically with it only through the layout frame and must not be drawn or hit-tested together. `maps[]` entries (in `/bootstrap` and `/human_view/window`) carry `space` too.
- `/bootstrap` gains `spaces: [{"space": 0, "map_id": "...", "kind": "overworld"|"interior", "bounds": [x0, y0, x1, y1], "origin": [ox, oy], "revision": n, "sha256": "..."}, ...]` (authored worlds only; absent flag off and in legacy worlds). `bounds` and `origin` are in the layout frame. Interior map bytes are served by `/map_file/{map_id}` (ETag as today).
- A portal use moves the actor in one tick to the target anchor and writes its `space` in that tick; the client switches its drawn space when the controlled actor's `space` changes. `POST /control/portal` keeps its request shape. A move by another path (god command) shows the new `space` one tick late.
- The physical contract in `spatial` is still the union contract of the whole authored world (correct because the regions are disjoint); a per-space contract is not planned before P5.
- Nothing else in the frame changes: walls, anchors and portals are in layout coordinates.

## 5b. Creatures (IMPLEMENTED, Phase 2, backend flag `EDEN_CREATURES=1` with `EDEN_WINDOW=1`; default off, with the flag off nothing below exists and every frame is byte-identical)
- **Ids.** Creatures are animals with `type_id` 40..79 (frozen; the list is `tests/fixtures/creatures_contract.json`, produced by `tools/export_creatures.py`: id, name, sprite path or null, frame, pivot, footprint, variants, enabled, flight, swim). New ids appear in `/frame` `animals[]` with the same keys as the legacy animals (`id`, `slot`, `type_id`, `type_label`, `x`, `y`, `hp`, `state`, `render`, `space`, ...); `type_label` is the species name. The five legacy species keep their numbers.
- **New key on an animal**, present only with the flag on and only for creature rows: `creature: {"species": "goblin", "sprite": "a4/static/static-sheep-a4-v1.png" | null, "footprint": [w, h], "state": "idle"|"wander"|"flee"|"chase"|"rest"|"return"|"attack" | null, "variant": "<variant name>" | null}`. `sprite` is null where there is no art yet (draw the footprint as a placeholder box of `footprint` units); `state` is null for sheep, deer, tiger, wolf and fish, whose behaviour still runs in the legacy loops; `variant` is null for the base form. It is nested because `state` is already the attribute dict of the animal. A client that does not know the key ignores it.
- Positions are window-local like every other row (a re-base shifts them; sections 4 and 5 apply). A creature never enters a wall box, an interior or a pocket, and never leaves the window frame; a flyer (`flight` true) passes rock, water and ruin boxes but not built or interior walls; a swimmer (`swim` true) stays on water tiles.
- **Event** `creature_killed {species, pos, killer_uid}` (queued once per dead creature; `killer_uid` is the killing creature's uid, null for a kill by a resident, hunger or age).
- **Saves.** The creature store is not saved. After Continue the creatures of the integrated chunks are generated again from the world seed: wounds, kills and where a creature had wandered are lost, and a creature that was killed returns after a reload. No refusal text; the save format is unchanged.

## 5c. Calendar (IMPLEMENTED, backend flag `EDEN_CALENDAR=1`; default off, with the flag off nothing below exists and every payload is byte-identical)
- `/bootstrap` `world.calendar = {enabled, profile, day_ticks, year_ticks, days_per_year, season_ticks, daylight, ticks_per_second, life_year_ticks}`: `profile` is `"user"`, a game day is 12000 ticks (10 minutes at 20 ticks per second), a year is 8 days (96000 ticks), `season_ticks` is 24000, `daylight` maps each season to the fraction of the day with the sun up (spring 0.50, summer 0.58, autumn 0.50, winter 0.42), `life_year_ticks` is the ageing unit (one life-year per game day).
- Every `/frame` (and the empty frame) gains `time = {tick, day, day_phase, block, season, season_phase, year, light}`: `day` and `year` are whole indices counted from tick 0, `day_phase` and `season_phase` are in [0, 1), `block` is `dawn | day | dusk | night` (dawn and dusk are 500 ticks each), `season` is `spring | summer | autumn | winter`, `light` is the sun's level in [0, 1] (0.05 at night, a quick dawn and a long bright middle). The client may draw the sky from `light` and `day_phase`; it may ignore the block.
- The existing `world.ticks_per_year` and the frame's `year` keep their meaning and carry the long calendar when the flag is on (96000 ticks per year).

## 6. Saves (IMPLEMENTED in P3)
- With `EDEN_SPACES` off the save format is unchanged (format 1). With it on, saves are format 2. A save of the other format is refused by Continue (HTTP 400, `detail` is the text; nothing is changed or deleted):
  - format 1 save, spaces on: *"This save was made by an earlier version of the game (world format 1), in which interiors shared the overworld's coordinate frame. This version keeps interiors as separate spaces (world format 2), so the save cannot be continued. Start a new world; the old save file has not been changed or deleted."*
  - format 2 save, spaces off: *"This save was made with separate interior spaces (world format 2, EDEN_SPACES=1), but this session runs without them, so it cannot be continued. Start the game with EDEN_SPACES=1 to continue it. The save file has not been changed."*
- `GET /session` `saves[]` entries (and `CheckpointStore.list_saves`) carry `compatible: true|false` when the backend runs with spaces, and for any format-2 save; the key is absent for format-1 saves in a session without spaces (absent means compatible). Entries from before the field count as format 1. The client can grey out an incompatible save instead of letting the player hit the refusal.

- Window saves (format 3) written while built structures are stored away from the player (`EDEN_STRUCTURE_STORE=1`, the dormant structure store) are **format 4**; an empty store still saves as format 3. A format 4 save in a session without the store (or without the window) is refused by Continue like the others (HTTP 400, nothing changed). Text for a session without the store: *"This save contains buildings stored away from the player (the dormant structure store), which this build cannot load, so it cannot be continued. Use a build with EDEN_STRUCTURE_STORE support, or start a new world. The save file has not been changed."* (without the window, the format 3 text above). `saves[]` still reports the session's format (3), so a format 4 save is listed as compatible and refused on Continue.
- Saves made under `EDEN_CALENDAR=1` carry an optional `calendar = {profile, day_ticks, year_ticks}` in the world format (no format number changes; a save without it was made with the original short calendar). Refused by Continue: a long-calendar save in a session without the flag: *"This save was made with the long calendar (a game day is 12000 ticks, EDEN_CALENDAR=1), but this session runs without it, so it cannot be continued. Start the game with EDEN_CALENDAR=1 to continue it. The save file has not been changed."*; a short-calendar save in a session with the flag: *"This save was made with the original short calendar (a game day is 2400 ticks), whose hunger, growth, weather and ageing rates differ from the long calendar (EDEN_CALENDAR=1), so it cannot be continued in this session. Start a new world, or start the game without EDEN_CALENDAR=1 to continue the save. The save file has not been changed."* (both texts approved by the user, USER-DEC-6).
